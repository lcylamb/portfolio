# 一百行的条件求值器，撑起整张动态表单

上一篇讲的是「为什么要重写」：一千三百行 if-else 表单，问题出在**规则被写死在代码里**。重写的结果是一份 schema——显隐、只读、条件必填，全部变成可序列化的数据。

但 schema 只是契约。契约不会自己执行。

真正让「动态」动起来的，是一个一百行左右的条件求值器。这篇就讲它：条件怎么表达，作用域怎么设计，以及几个看起来「偷懒」、实际上想了很久的决定。

代码在引擎的 `schema/conditions.ts`，全文可以一次读完。

## 一、条件的形态：一棵 JSON 树

先看条件长什么样：

```json
{ "field": "claimScene", "op": "eq", "value": "TRAVEL" }
```

这是原子条件。复合条件就是三种节点的嵌套：

```json
{
  "and": [
    { "field": "claimScene", "op": "eq", "value": "TRAVEL" },
    { "or": [
      { "field": "amount", "op": "gt", "value": 5000 },
      { "field": "hasInvoice", "op": "truthy" }
    ]}
  ]
}
```

设计上有两条硬约束，都写在了类型定义的注释里。

**第一条：必须能 `JSON.stringify` 走一遍再 `parse` 回来。** 这一条决定了条件不能是回调。`visibleWhen: (values) => ...` 写起来当然爽，但后端就再也没法下发条件、配置后台没法校验条件、服务端没法预检。第一篇里说的「把规则从渲染里剥出来」在这里兑现成：**规则必须是数据，而数据就不能藏函数。**

**第二条：节点用「可辨识联合」，不搞万能接口。** `and` / `or` / `not` / 原子条件四种形态各自持有不相交的字段，求值器里 `if ('and' in expr)` 之后 TypeScript 自动收窄，一个 `as` 都不用写。项目里满屏的 `(el as any)` 大多就是把「本可以收窄的联合」写成了 `string`，这里算是反向示范。

十二个算子：`eq / neq / in / nin / gt / gte / lt / lte / notEmpty / empty / truthy / falsy`。看着少，但表单联动需要的语义差不多就这些——多了不是表达力，是学习成本。

## 二、作用域：为什么先查局部、再查根

这是整个求值器里我认为最重要的一个设计。

列表项里的字段要引用兄弟字段。如果不做作用域，条件就得写完整路径：

```json
{ "field": "invoiceList.0.invoiceKind", "op": "neq", "value": "VAT_SPECIAL" }
```

这个写法毒在哪？**schema 是「每一项都长一样」的，写死下标等于把 schema 复制 N 份**——第 0 项一份、第 1 项一份，用户增删一行，所有下标全部失效。

所以求值时引入两层作用域：**先局部、后根**。

```ts
function resolve(scope: Scope, field: string): unknown {
  if (scope.local !== undefined && hasPath(scope.local, field)) {
    return getPath(scope.local, field);
  }
  return getPath(scope.root, field);
}
```

于是同一份条件 `{ "field": "invoiceKind", ... }`，在列表里指向本行，在根层指向顶层字段，schema 一个字不用改。这是声明式的红利：**作用域解析承担了位置，schema 就不用承担。**

两个容易做错的细节，都值得单独说：

**顺序不能反过来。** 先查根的话，只要顶层恰好有个同名字段，列表项就会静默读到外层的值。这种 bug 在页面上只表现为「偶尔显隐不对」，几乎无法定位——因为你查的是第 3 行，读到的却是第 0 层的值，谁会把这两个东西联想到一起？

**「局部有没有」必须用 `hasPath`，不能用 `getPath(...) !== undefined`。** 因为一个被显式写成 `undefined` 的字段，仍然算「局部有」，不应该穿透到根。这两种判断在 99% 的情况下结果一样，剩下 1% 就是那种查一个下午的 bug。这条差异我们用一个单测钉死了——不是因为聪明，是因为错过。

## 三、归一化：`'1'`、`1` 和 `true` 是一回事吗

不是一回事，但业务上是一回事。

表单里同一个含义的值有三种形态：下拉选出来存字符串 `'1'`，后端下发的枚举值是数字 `1`，开关存布尔 `true`。条件里写 `value: 1`，字段实际是 `'1'`，不归一化的话结果就是静默不匹配——页面上表现为「选了却没反应」，而且没有任何报错。

所以比较前统一折算：

```ts
function normalize(value: unknown): unknown {
  if (typeof value === 'number') return String(value);
  if (typeof value === 'boolean') return value ? 'true' : 'false';
  return value;
}
```

`eq / neq / in / nin` 都走这套。但数值比较**刻意不做**：

```ts
// 数值比较不做 normalize —— '10' > '9' 在字符串语义下是 false，而这里要的是 true
gt: (a, b) => toNumber(a) > toNumber(b),
```

原因是 `'10' > '9'` 在字符串语义下是 `false`（按位比字符 '1' < '9'）。如果先归一化再比，等于自己造了一个类型系统去猜用户意图。**每个算子只负责一种语义，语义边界写在算子里，不写在调用方的脑子里。**

## 四、两个「宁可多显示」的宽容决定

求值器里有两处返回 `true` 的兜底，第一次读代码的人多半会觉得奇怪：

```ts
export function evaluate(expr: ConditionExpr | undefined, scope: Scope): boolean {
  if (!expr) return true;          // 没写条件 = 永远成立
  if (isAtomic(expr)) {
    const operator = OPERATORS[expr.op];
    if (!operator) return true;    // 不认识的算子 = 成立
    ...
```

没写条件返回 `true` 好理解——「没有约束就是无约束」，调用方不必到处写 `expr ? evaluate(expr, scope) : true`。

不认识的算子也返回 `true`，这个要想一下。

场景是：后端先上了新算子（比如 `between`），前端还没发版。这时前端面对一条读不懂的规则，有两个选项——按 `false` 处理，字段消失；按 `true` 处理，字段照常显示。

**选后者。** 一条读不懂的规则，最坏结果是「多显示了一个本该隐藏的字段」；而一个字段因为前端不认识规则就整块消失，用户面对的是一份残缺的单据，还不知道缺了什么。表单是录入工具，**fail-open 的代价是多显示，fail-closed 的代价是数据残缺**——后者重得多。

当然这条有边界：如果将来出现「某个算子漏显示会资损」的场景，这个决定就要重议。宽容是方向，不是教条。

## 五、为什么不做依赖收集

这是我最常被问的一个问题：显隐联动不就是响应式吗？为什么不建一张「字段 → 依赖它的表达式」的反向索引，字段一变只重算受影响的条件？

答案是：**先算规模，再谈架构。**

现在的实现是每渲染一次、全量求值一遍所有条件。表单字段是百级，不是万级。一百次字符串比较的开销，大约相当于一次 `Array.prototype.sort`，远小于维护反向索引的复杂度——依赖什么时候注册、什么时候清理、列表增删行时索引怎么同步、循环依赖怎么办，每一条都是新的 bug 面。

全量求值最大的好处反而是**它没有状态**。条件求值是 `(expr, values) => boolean` 的纯函数，测试就是给输入断输出，不需要 mock 时序、不需要担心缓存失效。上篇说的「不变量写成测试」之所以做得到，很大程度上是因为这些纯函数根本没有需要 mock 的东西。

`collectReferencedFields()` 函数确实存在，它收集表达式引用的全部字段。但它现在只服务于两个低频场景：预置数据初始化、调试面板。**如果哪天字段真的到了万级，这个函数就是反向索引的现成起点。** 为还不存在的规模预先支付复杂度，是我从第一篇就在反对的事——if-else 的每一行都合理，提前优化的每一层架构也都合理，直到它们不合理。

## 代价

老规矩，成本说清楚。

**第一，求值顺序是隐式契约。** 「先局部后根」写死在 `resolve` 里，schema 作者必须知道这条规则才能预测条件会读到什么。新人写出「依赖根上同名字段」的条件时，行为是正确的但意图是错的——这种对，最难在 code review 里拦住。

**第二，宽容是有账单的。** 未知算子返回 `true`、`undefined` 视为成立，意味着 schema 里的笔误不会报错，只会静默放行。调试面板能缓解，但根子上我们选择了「宁可错放，不可错杀」，这类系统永远少了一层保险。

**第三，表达式没有编译期检查。** `field: "claimScence"`（拼写错）不会在 TypeScript 层报错——它是数据，不是代码。要根治得给 schema 加一层引用完整性校验（`collectReferencedFields` 对比字段表），这个在清单上，还没做。

一百行换来这些，值不值，取决于你的表单会不会长到第一篇那个一千三百行。会的话，这大概是性价比最高的一百行。
