# React Fiber：render 为什么可以停

> 学习笔记。上一篇垃圾回收讲的是引擎怎么**腾出**时间，这篇讲 React 怎么**用**这些时间——Fiber、时间切片、可中断渲染，其实都是同一个问题的三种说法：一帧只有 16.6ms，不够用怎么办。图是自己画的。

React15 之前（准确说是 Fiber 架构之前），一次组件树更新是**一口气算完**的：从根开始递归调和，整棵树比完、DOM 全部更新完，JS 才把主线程还回去。树小的时候没事；组件树深了、单次更新几十上百毫秒，用户输入、动画全被卡住——而且没有任何办法打断它，因为递归的状态就存在调用栈里，栈一断，算到哪了就丢了。

Fiber 要解决的就是这一件事：**把「不能停的递归」改成「随时能停、还能接着算的工作循环」。**

## 一、Fiber 是什么：同一个词的三层意思

「Fiber」这个词在 React 的语境里被用在三个地方，分开理解才不打架：

**一种架构。** React15 的 Reconciler 叫 Stack Reconciler——「栈」调和器，名字就说明了问题：执行状态压在调用栈上，递归开始就只能走到底。新架构改成了自己维护的调度循环，执行状态从栈里搬到了堆上。

**一种数据结构。** 每个 React element 对应一个 Fiber 节点，节点之间不再是函数调用的父子关系，而是三个指针连成的链表：

```typescript
interface Fiber {
  child: Fiber | null;    // 第一个子节点
  sibling: Fiber | null;  // 下一个兄弟
  return: Fiber | null;   // 父节点
  // ...
}
```

这一步是整个架构的地基：**递归之所以不可中断，是因为「算到哪了」记录在调用栈里；换成链表之后，「算到哪了」就是当前指向的节点，一个变量而已。** 停下来的时候把这个变量存好，回来接着走，天塌不下来。

**一个工作单元。** 每个 Fiber 节点还存着「这一轮要做什么」：props 变了什么、要不要移动 DOM（effectTag）、要挂载还是卸载。调度器每次取出一个节点处理，处理完看看时间，还有预算就继续，没有就让出去。

> 图 1 · 上半：Stack Reconciler 递归调用，A 调 B、B 调 C，中途无法停下；下半：Fiber 用 child / sibling / return 三个指针把树拍平成链表，工作循环在链表上逐步推进，随时可停

## 二、一帧的预算，和让出的时机

浏览器一帧的预算是 16.6ms（60fps），这一帧里排队的事情是固定的：处理事件 → 执行 JS → `requestAnimationFrame` 回调 → 样式计算 → 布局 → 绘制。JS 只是一个租客，不是房东。

如果本轮 JS 只花了 5ms，剩下 11.6ms 浏览器在等下一个帧开始——**这段时间就是 Fiber 想借的时间**。

React 的做法是把 render 拆成一个个小工作单元，每做完一个检查一次时间：

```javascript
function workLoop(deadline) {
  while (nextUnitOfWork && deadline.timeRemaining() > 1) {
    // 时间还有，处理下一个工作单元
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork) {
    // 预算用完了，登记下一帧继续
    requestIdleCallback(workLoop);
  }
}
```

这就是时间切片：一次 50ms 的整块 render，变成十几个 3~5ms 的小块，插进每一帧的空闲时间里。每一帧 JS 都在干活，但**没有哪一帧被独占**，输入事件照常响应，动画照常走。

![一帧 16.6ms 的预算与时间切片](/diagrams/fiber-frame-budget.svg)
> 图 2 · 上半：没有切片时，一次长 render 独占若干整帧，期间的输入事件和绘制全部排队；下半：切片之后，render 被拆成小块塞进每帧的空闲时段，输入和绘制不再被饿死

React 实际没有直接用 `requestIdleCallback`——它兼容性一般、触发频率跟屏幕刷新率不对齐、还可能被节流。React 自己用 `MessageChannel` 实现了一个调度器，语义上是同一个东西：**「主线程忙完这阵了，有空叫我」**。

顺带回答一个常见追问：**为什么不用 generator？** generator 确实能 `yield` 中途暂停，但它暂停的是函数调用栈，恢复时必须沿着同一个调用链往下走——做不到「暂停期间先去处理一个更高优先级的输入，再回来」。而且 generator 一旦中间某层被 try-catch 或别的逻辑包住，yield 的传播就被截断了。自己维护链表 + 显式存档，控制力完全不同。

## 三、两阶段：能停的和不能停的

Fiber 把更新分成两个阶段，边界画得很硬：

**render 阶段——可中断。** 对比新旧两棵 Fiber 树（就是 diff），给需要变更的节点打上副作用标记。这一阶段**不碰任何真实 DOM**，纯内存计算，所以随时可以停、可以扔掉重来。

**commit 阶段——不可中断。** 把 render 阶段收集的所有副作用一次性执行：真实 DOM 的增删改、`getSnapshotBeforeUpdate`、`useLayoutEffect`、然后异步地 `useEffect`。

为什么 commit 不能停？**因为用户看得见。** DOM 改到一半停下来，用户看到的是半新半旧的界面——布局对不上、事件监听挂了一半。render 算错了大不了重算，commit 错了是展示事故。所以 render 可以慢慢切片，commit 必须快、必须一次做完。这也反过来解释了一条实践建议：**commit 阶段的钩子（`useLayoutEffect`）里别做重活**，它在这条「不可中断」的通道上，做重了就等于把切片撕开一道口子。

### 双缓存：两棵树怎么换

render 是中断后恢复的，那「算到一半的新树」放哪？答案是两棵树：

- **current 树**：当前屏幕上正在显示的，commit 的产物；
- **workInProgress 树**：render 阶段正在内存里构建的。

render 在 workInProgress 树上推进（可以中断，无所谓，反正没上屏）；render 完成，commit 把 workInProgress 的副作用一次性打到屏幕上，然后两棵树交换角色——刚才的 workInProgress 变成新的 current，下一轮更新又在旧的 current 上开始构建。

![双缓存与两阶段](/diagrams/fiber-two-phases.svg)
> 图 3 · render 阶段在 workInProgress 树上推进、可中断可重算；commit 阶段把副作用一次性打到屏幕，两棵树交换 current / workInProgress 的角色

用双缓存理解「key 为什么必须稳定」也顺：diff 是在新旧两棵 Fiber 树之间比对的，key 是跨渲染认出「这还是那个节点」的唯一凭据。key 用数组下标，列表头部插一项，所有节点的「身份」整体错位——React 认不出谁是谁，只能把后面的节点全部当成新节点重建。

## 四、优先级：不是所有更新都一样急

切片让出了主线程，也带来新问题：render 中途来了一次更高优先级的更新怎么办？

Fiber 的调度器给任务分了优先级：用户输入这类同步交互最急；`useTransition` 包住的更新被标记为「过渡」，可以慢点算，被更急的任务插队就扔掉重来。这就是 `useTransition` 的由来——它不是性能优化语法糖，是把「这个更新不着急」这个信息交给调度器的接口。

大列表输入过滤是典型场景：输入框的受控更新必须即时，一万行的过滤结果可以慢慢算。以前要靠 debounce 硬凑，现在调度器自己会安排——先保证输入那帧不卡，过滤切片慢慢跑。

## 五、串起来看

| 概念 | 解决的问题 | 手段 |
| --- | --- | --- |
| Stack Reconciler → Fiber | 递归不可中断 | 调用栈 → 链表，执行状态搬到堆上 |
| 时间切片 | 长 render 卡帧 | 工作单元 + 空闲时间检查，5ms 一让 |
| render / commit 两阶段 | 一致性 | 纯内存计算可中断；DOM 操作不可中断 |
| 双缓存 | 中断后进度放哪 | workInProgress 树与 current 树交换 |
| 优先级调度 | 更新之间抢时间 | 同步更新 vs 过渡更新，可插队重算 |

落到日常，能用的结论：

**「setState 之后视图没有立刻变」不是 bug。** 更新进的是调度队列，render 会被切片、会被更高优先级的任务打断重来。对显示逻辑做「update 后立刻读 DOM」的假设，在并发模式下迟早出事。

**`useLayoutEffect` 里别做重活。** 它在不可中断的 commit 通道上，做重了等于自己把卡顿加回来。测量布局可以，跑计算不行。

**长列表慢，先想想 render 是不是纯计算太多。** 切片解决的是「不卡交互」，不解决「总耗时长」。虚拟滚动减节点数，`useMemo` 减重复计算，这些活 Fiber 替不了。

最后把两篇笔记连起来看：GC 的增量标记、三色标记，和 Fiber 的时间切片、可中断渲染，几乎是一对镜像——引擎在标记内存图的时候要「标一点、还一点时间」，React 在构建组件树的时候要「算一点、还一点时间」。**长任务切片化 + 显式存档进度，是主线程世界的通用解法**，想通其中一个，另一个就是免费送的。
