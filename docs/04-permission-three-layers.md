# 后台系统的权限，只做路由层等于没做

后台系统聊权限，十有八九聊的是「登录没登录、路由进不进得去」。但产品找过来的问题从来不是这种——是「复核岗为什么能点『退回重勘』」「这个人的列表里怎么有别的机构的单子」。

路由层一个都拦不住这些。

在保险中后台做了几年理赔系统之后，我的结论是：**权限不是一个开关，是三层各自独立的设计**——路由层管「能不能进这个页面」，按钮层管「能不能做这个操作」，数据层管「这条数据归不归你」。三层拦的东西不同，实现方式也不同，混在一起做的系统，每一层都是漏的。

## 一、路由层：登录态和权限是两回事

最常见的实现是路由表 + 守卫：

```tsx
const routes = [{
  path: '/claims',
  element: <ClaimsPage />,
  meta: { requiresAuth: true },
}];
```

外面包一层高阶组件，渲染前用 `useLocation` 拿到当前路径，匹配路由，看 `requiresAuth`，没 token 就 `<Navigate to="/login" replace />`。

这套能跑，但有两个问题要想清楚。

**第一，`requiresAuth` 管的是登录态，不是角色。** 「已登录的查勘员能不能进财务报表页」——这个问题 `requiresAuth: true` 回答不了，它只认识 token。要区分角色，路由 meta 里需要的不是布尔值，是**这页需要什么权限码**：

```tsx
meta: { permission: 'claim:review' }
```

守卫从用户信息里查有没有这个码。这两个概念在一个系统里同时存在很正常：登录页、个人设置页只要登录态；业务页面要权限码。**守卫逻辑一旦写成「有 token 就放行」，后面每个需要角色的页面都会自己再补一段判断，然后各自腐烂。**

**第二，守卫必须在渲染路径上，不能只在跳转时拦。** 用户收藏夹里存着 `/claims/audit/8842`，直接刷新进来——没有「点击菜单」这个动作给你拦截。所以判断必须长在组件渲染的必经之路上：要么高阶组件包路由出口，要么每个受保护页面自己先过一遍钩子。只在菜单点击时做校验的系统，权限名单和浏览器历史记录是两套互不相认的事实。

## 二、按钮层：前端只管藏，不管拦

路由管页面，但一个理赔详情页里，「通过」「退回」「升级」是三个操作，三个权限。

按钮层最顺手的形态是一个 hook / 指令：

```tsx
const can = usePermission();

{can('claim:rollback') && <Button onClick={rollback}>退回重勘</Button>}
```

或者 Vue 那边一个 `v-permission` 指令，挂在元素上没权限就摘掉。实现都简单，简单到让人忘记要想两件事。

**权限码从哪来。** 我的做法是登录后一次性拉取，塞进全局状态：

```json
{ "permissions": ["claim:view", "claim:review", "claim:rollback"] }
```

码由后端按角色算好下发，**前端不做「角色 → 码」的映射**。因为角色和权限的对应关系是业务规则，会变；前端硬编码一份，等于复制了后端的职责，还是份会过期的复制。前端只认识码，不认识角色。

**藏了按钮之后，操作还在吗。** 这是按钮层最容易被糊弄过去的问题：`display: none` 的按钮，它的接口还在。用浏览器开发者工具看一眼网络面板，谁都能直接 `POST /api/claim/rollback`。

所以按钮层这句话必须写在设计文档的第一行：**前端权限是体验层，不是安全边界。** 把按钮藏掉是为了让有权限的人少看到干扰、让没权限的人不至于点进去再吃一个 403；真正的拦截发生在后端——每个写接口校验权限码，越权返回 403。

判断一个系统权限做得对不对，别看它藏了多少按钮，看它**接口在裸调时会不会拒绝**。

## 三、数据层：同一个页面，每个人看到的世界不一样

前两层做完，还剩最难的一层。

同一个「待办列表」页，查勘员看到自己名下的单子，组长看到全组的，机构管理员看到整个机构的。页面是同一个，路由权限一样，按钮权限一样——**差别在数据**。

这种「行级权限」我倾向于完全交给后端：接口根据 token 里的身份决定查询范围，前端根本不知道「数据范围」这个概念的存在。前端一旦试图自己过滤（拿到全量列表再 `filter`），就埋了两颗雷：一是分页算不准——过滤掉的行还占着页容量；二是越权数据已经到了浏览器里，等于没拦。

字段级的控制比行级更细：复核岗能看到金额、历史理赔次数；录入岗看不到。这类需求在保险系统里很常见，也最容易和「编辑权限」搅在一起。

这里有个从表单引擎里学来的区分，直接搬过来用：**「能不能编辑」和「要不要提交」是两件事。** 无权限编辑的字段应该只读展示、原样提交——如果把它当成「用户清空了」从提交体里删掉，后端收到的就是一条数据残缺的单据，而且查不出是谁删的。混用这两个语义的系统，迟早会把「没权限改」误传成「有人改过」。

## 四、权限码的粒度，在第一次需求变更前就想好

码怎么设计，决定这套系统能撑多久。

太粗（一个模块一个码）会把不该绑的操作绑死：`claim:write` 同时覆盖了「新建」和「退回」，产品说「录入岗不能退回」时你只能加新码、回头改所有配置。太细（一个按钮一个码）会让配置变成体力活，运营在权限管理页里面对两百个复选框，没人知道哪个该勾。

我的经验是按「**资源 + 动作**」取中间值，动作只保留真正会独立授权的那几个：

```
claim:view        看列表和详情
claim:edit        新建 / 修改草稿
claim:review      复核（通过 / 退回）
claim:pay         涉及打款的操作
```

有没有 `claim:rollback` 这种独立码，不取决于技术审美，取决于**会不会有人单独拥有它**。答案是会，就拆；不会，就并。权限码是给运营配置用的词汇表，词汇表大小应该跟着组织结构走，不跟着按钮数量走。

## 最后

把三层摊开看，会发现一个共同点：**前端在每一层里都只负责「让该看见的人看见」，没有任何一层负责「让不该的人做不了」。**

这不是前端偷懒。这是权限系统的正确形状——展示控制越靠前端越便宜，安全边界必须越靠后越结实。前端权限做满了（路由、按钮、字段全部控制），接口裸调照样要拦；反过来，后端拦得再死，前端不控制展示，用户面对的就是一个全是 403 的系统。

所以每次有新人问「前端权限是不是可以随便绕过，那做了还有什么用」，我的回答都一样：它防的本来就不是绕过的人，它防的是误点的人。防绕过，从来就是接口的活。
