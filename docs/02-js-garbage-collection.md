# JS 垃圾回收机制：从引用计数到 V8 分代回收

> 学习笔记。主要参考《深入理解 V8 JavaScript 引擎》和浏览器内核那几份资料，图是自己画的，例子都能跑。

写 JS 不用管内存。声明一个对象，用完，不管它，它最后会被收走。收走这件事由垃圾回收器负责，实现藏在宿主环境里——浏览器和 Node.js 各自调引擎，V8 是其中一个。

判定「垃圾」只有一句话：这个对象还能不能被访问到。能访问就留着，访问不到就清掉。判定不难，难的是判得便宜，以及清完之后内存怎么收拾。

围绕判定方式，主流走过两条路：引用计数、标记清除。V8 在标记清除之上又加了一层分代。按这个顺序捋下来，很多东西才讲得通。

## 一、引用计数：数有几个人在用它

思路最直接。每个对象记一个数字，被引用一次加一，引用失效减一，减到零就是垃圾，当场回收。

```javascript
let a = { name: '对象 A' }; // A 被引用 1 次
let b = a;                  // A 被引用 2 次
b = null;                   // 1 次
a = null;                   // 0 次 → A 是垃圾，立刻回收
```

好处是即时。归零就收，不用等时机，主线程也不会在某一次集中回收时被卡住。

问题是循环引用，这是引用计数的死穴：

```javascript
function fight() {
  const objA = {};
  const objB = {};
  objA.ref = objB; // A 引用 B
  objB.ref = objA; // B 引用 A
}
fight(); // 函数执行完，外部再也拿不到 objA / objB
```

`fight()` 一返回，外部就再也拿不到这两个对象了，它们理应是垃圾。但两个对象互相引用，各自的计数永远是 1，永远归不了零。函数每调一次，泄漏两个对象。早期 IE 的 DOM 对象就栽在这个坑里。

这条路走到这儿就断了。

## 二、标记清除：从「有人引用它吗」换成「还能找到它吗」

换了个问法。不看谁引用它，看从根对象出发还能不能到达它。根对象是全局对象、当前调用栈里的局部变量这些。

从根出发递归遍历，能到达的对象标成「在用」；遍历结束，没被标上的就是垃圾，统一清除。

循环引用在这里自动失效：`fight()` 返回后，从根到 `objA`、`objB` 的路径已经断了，遍历根本走不到它们，两个都不标记，一起回收。

![标记清除法的可达性判断](/diagrams/gc-reachability.svg)
> 图 1 · 从根对象出发做一遍可达性遍历：绿色的被标记为存活，红色的那对循环引用对象不在引用链上，一起被回收

也解释了另一件事：给变量赋 `null` 常被叫作「手动断开引用」，它断的不是计数，是可达性。

### 2.1 代价一：内存碎片

标记清除不搬动对象，清掉哪块就空哪块。空块散落在存活对象之间，内存就不连续了——这就是碎片。

碎片本身不致命，致命的是它让后续分配变难：要申请 200KB，剩下的空闲块单块都不够，明明总量够却分配不出来。于是有了「从空闲列表里挑哪一块」的三种策略：

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| First-fit | 找到第一块大于等于所需空间的空闲块，立即返回 | 分配效率最高，但留下的小尾巴多 |
| Best-fit | 遍历整个空闲列表，找到大于等于所需空间的最小块 | 空间利用率最高，但要遍历全表，慢 |
| Worst-fit | 遍历整个空闲列表，找到最大的块，从里面切出所需大小 | 切剩下的一半仍然很大，还能继续用 |

实际实现以 First-fit 为主，效率优先；找不到合适的再落到另外两种。但这三种都只是缓解，碎片一直存在——根子在内存不连续。

![内存碎片与标记整理对比](/diagrams/gc-fragmentation.svg)
> 图 2 · 上半是标记清除之后的内存：空闲块零散，总量够却没有单块能满足申请；下半是标记整理之后，活动对象挤到一端，空闲内存连成一整块

### 2.2 代价二的对策：标记整理

既然问题是「清完之后不连续」，那就清完再收拾一遍。标记整理（Mark-Compact）的标记阶段和标记清除完全一样，区别在标记之后：先把活动对象全部推到内存一端，然后清理边界外那一整块。

移动之后对象紧挨着排，空闲区连成一整块，碎片没了。代价是搬动对象本身不便宜——所有指向这些对象的引用地址都要跟着改。所以标记整理一般不做成每次回收的默认动作，只在需要时执行。V8 的老生代就是这么用的，下面会讲到。

## 三、V8：分代回收

前面这些算法有个共同的浪费：每次回收都要检查堆里全部对象。

可对象和对象不一样。事件回调里临时造出来的，活几毫秒；全局配置、缓存，页面活着它就活着。用同一套频率去扫这两类对象，怎么算都不划算。

V8 的办法是按存活时间把堆分成两块：新生代、老生代。各用各的算法，各按各的频率收。

![V8 分代回收总览](/diagrams/gc-generations.svg)
> 图 3 · V8 堆的分代结构：新生代跑 Scavenge + 并行回收，老生代用标记清除 / 标记整理 / 增量标记，满足条件的对象从新生代晋升上去

### 3.1 新生代：Scavenge，把活的搬走

新生代放的是短命对象，绝大多数对象死在这里，所以这块回收特别频繁。

对象都朝生夕死，那就别在原地标记清除了，直接把活着的搬走——Scavenge 算法，典型实现是 Cheney 复制算法。

内存一分为二：使用区（From）和空闲区（To）。流程是这样：

1. 新对象都分配在使用区；
2. 使用区快满时触发回收；
3. 对使用区里的对象做一次标记；
4. 把标记为活动的对象复制到空闲区。复制不是原样搬运，而是从根开始按引用关系边遍历边排，落进空闲区时天然紧凑相邻——不需要再单独整理；
5. 使用区整块清空；
6. 两区互换角色，下一轮反着来。

说白了是拿空间换时间：永远只用到一半内存，但回收时只碰活对象，死对象一个都不用管，也不会留下碎片。

![Scavenge 算法的三步](/diagrams/gc-scavenge.svg)
> 图 4 · Scavenge 的三个阶段：标记 → 把存活对象复制到 To 区并紧凑排列 → 清空 From 区、两区角色互换

一个对象要晋升到老生代，满足下面任一条即可：

**活得够久**。经历多次 Scavenge 还活着，说明生命周期长，没必要每轮都陪着搬来搬去。

**To 区占用要到 25%**。复制过程中如果晋升的对象会让空闲区使用率超过 25%，也直接晋升。因为下一步就要角色互换，它所在的区域马上变成新的使用区；占比太高，剩余空间太小，后续分配会明显变慢。

新生代回收频繁，如果每次都让主线程停下来做，卡顿会很显眼。所以 V8 起多个辅助线程并行做标记和复制，主线程只在少数关键步骤上同步。

### 3.2 老生代：两板斧加一个增量标记

老生代放长命对象——晋升上来的，以及直接分配的大对象。体积大，收得少。

它用的就是前面那两板斧：以标记清除为主；碎片多到影响分配时，用标记整理把对象搬到一起。

麻烦在停顿。老生代体积大，全量标记清除一次不短，一口气做完主线程要停几十上百毫秒——60fps 的页面上就是肉眼可见的卡。

于是有了增量标记：把标记过程切成很多小步，标一点就把主线程还回去执行一段 JS，交替进行。一次长停顿变成很多次几毫秒的短停顿，用户感觉不到。

### 3.3 三色标记：标记做到一半，进度记在哪

增量标记带来一个新问题：标记不再是一口气完成的，中途会被打断，去做别的，再回来接着标。那「标到哪儿了」记在哪？

原来的「已标记 / 未标记」两个状态不够用了，中间必须有第三种：

白色是还没访问到的，标记结束时仍然是白色的就是垃圾；灰色是自己被访问到了、但它引用的子对象还没扫完；黑色是自己和它引用的所有对象都扫完了。

![三色标记法与写屏障](/diagrams/gc-tricolor.svg)
> 图 5 · 上半是三种状态的含义；下半是一次「标记到一半」的堆快照：灰色对象 B 就是断点，而写屏障负责拦住 A 新增的白对象引用

中断那一刻的进度就落在灰色对象上。恢复时从灰色对象继续往下走；全部扫完，堆里没有灰色，剩下的白色就是这一轮要清的垃圾。

但增量标记（以及后来的并发标记）留了一个口子：标记暂停期间，业务代码还在改引用关系。最典型的漏标场景是一个黑色对象新增了对白色对象的引用——黑色对象已经扫完，不会再被回头看：

```javascript
// 标记暂停期间用户代码执行：
blackObj.child = whiteObj; // 黑 → 白 的引用，这条边不会被重新扫描
```

恢复标记后没人回头检查这个黑色对象，它新指向的白色对象就会被当成垃圾误删。堵这个口子的是写屏障：在「往对象属性里写引用」这个动作上挂钩子，一旦出现黑对象引用白对象，立刻把那个白对象改灰，强制它进入下一轮扫描。有写屏障兜底，增量标记才敢和业务代码交替跑。

## 四、串起来看

| 阶段 | 策略 | 核心思想 | 解决了什么 | 留下了什么问题 |
| --- | --- | --- | --- | --- |
| 1 | 引用计数 | 引用为 0 即垃圾 | 回收即时 | 循环引用永远不回收 |
| 2 | 标记清除 | 从根出发看可达性 | 循环引用 | 内存碎片、分配慢 |
| 2.5 | 标记整理 | 活动对象向一端移动 | 碎片 | 移动对象本身有开销 |
| 3 | V8 分代回收 | 按存活时间分新生代 / 老生代，各用各的算法 | 不必要的全堆扫描 | — |
| 3.1 | 新生代 Scavenge | From/To 复制 + 并行回收 | 回收快、无碎片、不卡主线程 | 空间利用率 50% |
| 3.2 | 老生代 | 标记清除 + 标记整理 + 增量标记 | 大堆回收不卡顿 | 需要三色标记 + 写屏障记账 |

落到日常写代码，能用的结论没几条：

循环引用在今天不会造成泄漏，标记清除解决的就是它。但定时器、事件监听、闭包里长期持有大对象，照样会让对象一直可达，回收不掉。

挂在 `window` 上的缓存是天然的常驻对象，该清的时候得显式置 `null` 断开可达性。

热路径上别反复创建大对象。它们即使能被回收，也会让新生代 GC 触发得更勤——回收本身不贵，贵的是频率。
