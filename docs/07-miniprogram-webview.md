# 小程序里嵌 H5：通信的两条路和四个坑

> 实践笔记。业务里有一批页面同时要在小程序里跑、也要在浏览器里跑（活动页、内容页这类「运营要快」的场景），于是它们以 H5 形态开发，用 web-view 嵌进小程序。这篇记的是两个容器之间怎么传数据，以及几个当时让我们查了半天的坑。

web-view 一嵌，问题立刻出现：小程序和里面的 H5 是两个隔离的 JS 环境，变量不共享、事件不通，互相看不见。所有协作——传登录态、同步页面状态、把 H5 里的操作结果带回小程序——都要通过显式的通信通道。

通道只有两条：H5 → 小程序，和小程序 → H5。两条路的能力完全不对称，这是理解一切的起点。

## 前提：能嵌，本身就有门槛

先说三件配置层面的事，不然后面全是空谈：

1. **H5 的域名必须配置在小程序后台的「业务域名」里**，还要下载校验文件放到域名根目录。域名不对，web-view 直接白屏，报错还很不友好。
2. **H5 里要引入微信 JS-SDK**，通信 API 全在 `wx.miniProgram` 命名空间下。
3. **个人主体的小程序没有 web-view 权限**——这是企业主体的能力。

## 一、H5 → 小程序：一条「延迟到达」的消息

H5 往小程序发消息，API 是这个：

```javascript
// H5 页面里
wx.miniProgram.postMessage({
  data: { type: 'form_submit', result: 'approved', ts: Date.now() },
});
```

看起来像 `postMessage` 就该像 WebSocket 一样实时送达——**它不是**。小程序侧虽然在 `web-view` 组件上挂着 `bindmessage` 监听，但消息**不会**在 postMessage 的那一刻到达，而是要等到下面这些时机之一：

- 小程序页面后退或销毁；
- 用户在 web-view 里点分享；
- 组件销毁。

也就是说，消息是**攒着的**，触发时机一到，一次性把期间积累的所有 postMessage 按顺序交给小程序。我们第一次接的时候就在这里摔了：H5 里提交完表单立刻 postMessage，小程序侧监听函数纹丝不动，怀疑了半天域名配置和 SDK 版本——都不是，纯粹是消息还压在路上。

这个设计决定了它的用法：**postMessage 适合传「结果」，不适合传「事件」。** H5 里填完一整份资料、点完提交，把最终结果攒一条消息带回去，没问题；想做「H5 里点一下按钮，小程序立刻弹 toast」的实时联动，这条路走不通。

那实时联动怎么办？活在 API 面上找：`wx.miniProgram.navigateTo` / `navigateBack` / `switchTab` 这些**导航类方法是实时生效的**。所以「H5 完成任务 → 通知小程序」的实时写法实际是：

```javascript
// H5 里：带着结果跳转回小程序的某个页面
wx.miniProgram.navigateTo({
  url: `/pages/result/result?status=approved&id=8842`,
});
```

导航即通知，参数即消息。不优雅，但它是实时的。

## 二、小程序 → H5：其实只有 URL

反方向的通道更窄：小程序往 H5 传数据，**官方通道就是 URL 参数**。

```html
<!-- 小程序 wxml -->
<web-view src="https://example.com/page?token={{oneTimeToken}}&from=mp" bindmessage="onMessage" />
```

H5 在启动时解析 `location.search`，拿到入参。想在中途给 H5 传新数据？没有直连 API，实际做法是改 web-view 的 `src`（带上新参数重新加载）——页面会刷新，所以这只适合「换一个上下文」，不适合「推送一条更新」。

URL 传参有两个必须想清楚的点：

**别把长效 token 放 URL 里。** URL 会进网关日志、埋点日志、浏览器历史。需要在小程序和 H5 之间打通登录态时，推荐的做法是小程序侧先 `wx.login()` 拿 code，发给自己的后端换一个**短时效的一次性票据**，把票据放进 URL；H5 启动后拿票据找后端换真正的会话。票据一次性、几分钟过期，泄漏了也用不了。后端用 code 走 `jscode2session` 换 openid 那套流程不变，只是多了一层「票据换会话」的中转。

**参数是初始化契约，版本要对齐。** H5 会随着发版改参数名，小程序的发版节奏却不一样。旧小程序 + 新 H5 的组合随时可能出现，所以参数解析要宽容：缺参数走默认值而不是抛错，多余参数忽略。两端发版不同步是常态，代码得为这个常态设计。

## 三、四个真实的坑

**坑一：postMessage 不实时。** 上面说过了，单独立一条是因为它太出名。团队里每个新接 web-view 的人都要摔一次。记住这句话就行：**bindmessage 收到的是历史消息的批量回放，不是实时推送。**

**坑二：消息时机和导航时机打架。** 「H5 填完表单，postMessage 带回结果，然后小程序跳到结果页」——如果 postMessage 之后紧跟 `navigateBack`，消息会在后退的那一刻随 bindmessage 到达，时序刚好。但如果 H5 直接调 `navigateTo` 去结果页，原页面销毁也会触发 bindmessage——两个通道同时有数据，小程序侧要做好「同一件事从两条路到达」的去重。

**坑三：返回即白屏或返回不出去。** web-view 里点 H5 的链接会层层 push 历史，用户按小程序的返回，有时退的是 H5 的历史而不是小程序的页面——体验上就是「按了返回还在原地」。需要在 `bindload` / 返回时机上做处理：H5 第一层历史时返回应该退小程序页面。这个行为微信各版本有过调整，上线前在真机上按返回链路走一遍是必须的。

**坑四：业务域名是硬约束。** H5 内部跳转到未配置的域名，web-view 直接拦掉。活动页经常外链第三方落地页——要么把所有可能跳到的域名提前收集齐、全部配进业务域名，要么把这些跳转收敛回小程序自己的页面。上线前拿正式域名全链路点一遍，比什么文档都可靠。

## 四、什么该放 H5，什么该放小程序

最后回到架构选型。web-view 嵌 H5 不是免费午餐：拿不到小程序原生组件的性能、受业务域名约束、通信还是单向窄带。我的判断标准是**改动频率和平台耦合度**：

运营活动、内容展示、规则说明这类**高频改版、无需深度系统能力**的页面，放 H5，发版节奏和前端解耦，值得隔离的代价；

支付、授权、地图、蓝牙这类**重度依赖微信能力**的交互，放小程序原生页面，别在 web-view 里绕。

两边交界处的那条通信通道，能窄用就窄用：传结果、传票据、传上下文，一次说清楚；把「实时联动」设计进方案之前，先想想是不是架构放错了位置。
