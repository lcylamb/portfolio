# 我把一千三百多行的 if‑else 表单，重写成了一份 JSON

「费用填报」是财务中台里最硬的一块。一个页面，字段数按报销场景浮动，显隐、必填、联动，全部由后端下发——听起来是个标准的动态表单。

但它不动态。

产品提「给这个下拉加个联动」，我们回「要排期」。加一个字段的特殊交互，要改前端、发版、等测试。

所谓动态，动态的只是**数据**，行为全写死在代码里。

这个页面在 `Expense/FormList.tsx`，一千三百多行。

> 说明：字段名、文件名和业务域都做过脱敏，换成了结构同构的报销场景。行数、代码骨架、四个问题、三个决定都是原样。

## 先看它长什么样

那一千三百多行里，绝大部分是这一个函数：`buildFieldList`，从第 70 行开始，到第 1200 行结束。

它的骨架其实很朴素，只有两层判断：

```tsx
const buildFieldList = (field, name, listName) => {
  let { fieldKey, requiredFlag, editableFlag } = field;
  let required = requiredFlag === 1;

  // 第一层：按「字段名」逐个硬编码
  if (fieldKey === 'claimScene')   return <FieldSelect ... />;
  if (fieldKey === 'agentPayFlag') return <FieldSwitch ... />;
  if (fieldKey === 'departDate')   return <FieldDate ... />;
  // …… 二十来个
  if (fieldKey === 'vendorName' && listName === 'vendorDtoList') return ...;

  // 第二层：按「数据类型」兜底
  switch (field.valueType) {
    case 'select': ...
    case 'date':   ...
    default:       return <FieldText ... />;
  }
};
```

**先按字段名撞，撞不上再按类型兜底。** 这个顺序本身就是全文的问题所在：它承认了「同一个 `valueType`，只要字段名不同，行为就可以完全不同」。

旁边还有一个文件，`request.ts`，里面躺着这么一张表：

```ts
export const dependentFields = {
  hasInvoice: [           // 是否已取得发票
    { fieldKey: 'invoiceDate',  label: '开票日期', valueType: '' },
    { fieldKey: 'invoiceTitle', label: '发票抬头', valueType: 'string' },
    { fieldKey: 'invoiceNo',    label: '发票号码', valueType: 'string' },
  ],
  hasTrip: [ /* 4 个字段 */ ],
  hasEntertain: [ /* 2 个字段 */ ],
  agentPayFlag: [ /* 1 个字段 */ ],
};
```

这张表的意思很直白：**「谁依赖谁」是一条业务规则，但它被手写在了前端。** 一共 15 个字段的依赖关系。

## 问题一：所谓「动态」，动态的范围是被围死的

后端下发的字段长这样——这是前端定义的接口，对应接口真实返回的字段：

```ts
export interface FieldConfig {
  fieldKey: string;
  valueType: string;     // 控件类型 + 正则，挤在同一个字段里
  options: string;       // 枚举，逗号分隔
  requiredFlag: number;  // 静态：要不要填
  editableFlag: number;  // 静态：能不能改
  label: string;
  orderNo: number;
  // ……
}
```

前端拿到它之后，第一件事是拿 `fieldKey` 去撞那二十个 `if`。

所以后端能控制的是「**字段出不出现、要不要填**」，控制不了「**新字段长什么样**」。后端新配一个字段，它只会渲染成 `default` 分支里的文本框——因为没有任何一个 `if` 认识它。

那「依赖关系」呢？**契约里没有这个维度。** 没有 `dependsOn`，没有 `visibleWhen`，没有 `requiredWhen`。只有 `requiredFlag` 这种**静态**标志位，它只能表达「要不要填」，表达不了「**什么时候**要填」。

而业务要的恰恰是后者：报销人勾了「代他人提交」，实际报销人的账号才必填。

所以前端补了那张表。

有意思的是对比：**同一份数据里，枚举值是从后端拉的**（`fetchDict({ dictCodes: [...] })`），而依赖关系是写死的。

一个是业务规则，另一个也是业务规则。一个走后端，一个走代码。

差别不在于谁偷懒，**在于后端契约里有没有装它的那个字段**。

（也因此，这个问题的正确写法不是「前端为什么把规则写死了」，而是「契约为什么要补一个维度、补的成本有多高」。前者只能得出「改吧」，后者才决定了改不改得动。）

## 问题二：一个字段名，两套语义

`vendorName` 在这个文件里出现了两次，行为完全相反。

第一次在行程列表里，供应商名称：

```tsx
value: field.vendorName,
```

存的是**名字**。

第二次在供应商下拉里：

```tsx
value: field.id,
onChange: (_, option) => {
  const list = form?.getFieldValue('vendorDtoList');
  list[name] = { ...option, vendorId: option?.id, vendorName: option?.title };
  form?.setFieldValue('vendorDtoList', list);
},
```

存的是 **id**，而且顺手把整条 option 反写回了列表项。

同一个 `fieldKey`、同一个 `valueType`，语义相反。**唯一能区分它们的，是外层传进来的 `listName`。**

于是 `buildFieldList` 的签名里必须多带一个参数，只为了在渲染层做这种判别。

问题出在哪？**控件的「值语义」被字段名隐含了。** 字段名 `vendorName` 不承载「这里该存 id 还是存名字」，这个信息只存在于那两段 `onChange` 里。任何想复用这个字段的人，都得先读一遍它的实现，才知道它到底往里写什么。

## 问题三：隐藏 ≠ 不提交

这个文件里有**两种**让字段「看不见」的机制，而且两种都不阻止提交。

**第一种**，`valueType === 'hidden'`：

```tsx
if (field.valueType === 'hidden') {
  return <Form.Item name={[index, field.fieldKey]} hidden key={field.fieldKey} />;
}
```

`hidden` 只是加了个样式。值照样在表单状态里，照样提交。

**第二种**，条件渲染里不满足就 `return null`：

```tsx
<FieldDependency name={['tripDtoList']}>
  {({ tripDtoList }) => {
    if (tripDtoList[name]?.tripFlag !== Status.YES) return undefined;
    return <>{/* 出发日期、行程天数…… */}</>;
  }}
</FieldDependency>
```

组件不渲染了，但 **Form.List 里那些值还在**。

推演一下会发生什么：用户先按「差旅」填了一遍，填了只属于差旅分支的字段；改成「招待」，又填一遍；再切回差旅——**那些值一直都在**。

如果原样提交，一张差旅行程就会带上招待的字段。而**两边都是合法值**，后端校验拦不住——它收到的是一条业务上不该存在的数据。

这里得说清楚一件事：**`hidden` 在这套代码里的语义其实是「要提交，但不展示」。**

看 `dependentFields` 里那些字段就明白了：`costCenterId`、`vendorId`、`vendorCode`，`valueType` 全是 `hidden`——它们是后端**必须收到**的值，用户看不见、也不能改，但必须跟着提交上去。

所以真正的问题不是「hidden 没做过滤」，而是：**「必须提交的隐藏值」和「不该提交的隐藏值」这两种完全不同的意图，共用了同一个机制。** 前端分不清，后端也就分不清。

## 问题四：一个字段，扛着两件事

`valueType` 这个字段里，同时装着**控件类型**和**校验正则**：

```tsx
let rules = [{ required, message: '请输入!' }];

if (field.valueType.split('reg-')[1]) {
  rules.push({
    pattern: RegExp(field.valueType.split('reg-')[1]),
    message: '请输入正确的格式',
  });
}
```

而主渲染用的是**精确字符串匹配**：

```tsx
switch (field.valueType) {
  case 'select-m':      ...
  case 'select':        ...
  case 'YES_OR_NO_FLAG':...
  case 'date':          ...
  case 'number':        ...
  case 'datePikcer':    ...
  default:              return <FieldText ... />;
}
```

对上了吗？`'select-reg-^\d{11}$'` 不等于 `'select'`。它不等于任何一个 `case`。

**所以它必然落进 `default`，被渲染成一个文本框。**

真正的后果不是「正则失效」，而是：**想给一个字段配正则，就得放弃它的控件类型。** 一个下拉框配了正则，会变成一个输入框。

（说句公道话：如果后端的约定本来就是「`reg-` 只配给纯文本字段」，那这套设计**是对的**——`string-reg-xxx` 落进 default，得到「文本框 + 正则」，正合意图。一个字段扛两件事，在可能的组合很少时是省事的。它的问题在于表达力有边界：一旦出现「下拉 + 正则」这种交叉组合，就表达不出来了。**这是取舍的边界，不是失误。**）

顺便，这段「从 `valueType` 里抠正则」的代码，在这个项目里**被抄了 5 份**——`FormItem.tsx`、`FormList.tsx`、`Bill.tsx`、`PayInfo.tsx`，还有一个在别的页面目录里。

再顺便一个细节：`case 'datePikcer'`。拼写是错的，正确的是 `datePicker`。而它在两个文件里各有一份。

**一个拼写错误，被固化成了前后端的配置协议**——你现在把这个字改对，后端配置就全挂了。配置协议的发布是不可逆的，这是它的代价之一。

## 重写：把「规则」从「渲染」里剥出来

上面四个问题看着散，其实是同一件事：**「这条规则是什么」和「怎么把它画出来」缠在了一起。**

所以我重写时只定一个目标：**把规则从渲染里剥出来，让它变成数据。**

具体是三个决策，每个都有代价。

### 一、条件必须可序列化，所以做不了回调

显隐、只读、条件必填，全部退化成声明式表达式：

```json
{ "field": "claimScene", "op": "eq", "value": "TRAVEL" }
```

支持 `and` / `or` / `not` 嵌套，但**不支持函数**。

**代价**：写不了「金额大于前三项之和」这类规则。

**为什么接受**：一旦允许传函数，schema 就不再是数据了——配置后台、权限校验、服务端预校验，全部无从谈起。这是有意砍掉的能力，不是漏了。

### 二、取值「先局部、再根」

列表项里的 `expenseType` 指向本项，列表外的 `claimScene` 指向根。否则每加一层列表，schema 就得复制一份。

**这里有个必须写死的细节：顺序不能反过来。** 先查根的话，只要顶层恰好有个同名字段，列表项就会静默读到外层的值——而这种 bug 在页面上只表现为「偶尔显隐不对」，极难定位。

还有一条：「字段是否存在」必须用 `hasPath()` 判断，不能用 `getPath() !== undefined`。因为一个被显式写成 `undefined` 的字段，仍然算「局部有」，不该穿透到根。

**代价**：多了一条必须解释的求值规则，新人心智负担 +1。

### 三、把「被校验 ⇔ 被提交」写成不变量

这一条直接回应问题三。

校验和序列化各自解析一遍可见性，两者必须语义一致，所以定成不变量：

> 一个字段被校验 ⇔ 它出现在提交体里。

例外只有两处，而且都是刻意的：**只读字段**，和**表格里被锁定的单元格**——它们提交，但不校验。因为「用户改不了」和「后端不需要它」是两件事；混在一起，前端就会把「没权限改」误传成「用户清空了」。

最关键的一步是：**这条不变量被写成了测试。**

因为我第一版就是错的。我一开始按 `editableWhen` 去过滤表格单元格——这等于把「能不能编辑」和「会不会提交」当成一回事，直接打破了不变量。**是测试先发现不对的，不是我看代码看出来的。**

不变量不写测试，就等于没有。这句话听起来像常识，但只有被它救过一次的人才会真的信。

## 代价

上面三节都在讲收获，但抽象不是免费的，这一节得说清楚成本。

**第一，读代码的成本被转移了，没有消失。** 原版那二十个 `if`，新人扫一眼就知道某个字段渲染成什么。现在要读懂一个 schema 解析器、作用域回退规则、求值顺序。**对于熟练的人是收益，对于新人（包括三个月后的我自己）是成本。**

**第二，表达力有天花板，而且这个天花板是主动设计的。** 见前面第一节。

**第三，抽象成立的前提是「需求本身是同构的」。** 报销字段看着千奇百怪，剥掉业务外壳之后，大多逃不出那几种：下拉、日期、数字、联动、列表。**但如果你的字段每个都是特例，那就抽不出 schema——硬抽的结果是造出一堆 escape hatch，比一堆 if-else 更难维护。**

所以真正该问的问题不是「能不能抽象」，而是：**这条规则应该属于谁——前端代码、配置后台，还是后端字段字典？**

## 我没做的事

**没用现成的低代码平台 / 表单引擎。**

理由不是「太重」。是因为这套字段的显隐依赖的是**单据上下文**——费用类型、报销场景、审批状态，全在单据数据里。引入一个表单平台，就得把整个业务上下文也塞进去，那不过是换个地方写 if-else。

**没有直接替换线上那份旧代码。**

这个得说明白：**从零重写一个已经被业务依赖的复杂表单，风险极高。** 我做的这个引擎是一个可运行的验证，不是一次上线。

如果真要替换，路径大概是：

1. **先把纯逻辑从旧代码里抽出来**——条件求值、校验、序列化。让旧的渲染层继续用它们。这一步能立刻拿到单测覆盖，而且**不改变任何行为**，风险最低。
2. **再逐个列表迁移**到 schema 渲染，一次一个，新旧并存。`invoiceList` 一个、`vendorDtoList` 一个。
3. **最后删掉旧分支。**

我选这个顺序，是因为它每一步都可回退。而「一次性重写然后祈祷」不可回退。

## 最后

这个文件最难改的地方，不是它长，是它**每一行都合理**。

每一个 `if (fieldKey === 'xxx')` 都能追溯到某一次真实需求。它不是被人写坏的，它是一百次正确的改动叠出来的。

所以重构它靠的从来不是「看代码不顺眼」，而是先回答那一个问题：

**这条规则应该属于谁——前端代码、配置后台，还是后端字段字典？**

想清楚了这个，代码怎么改是顺带的事。
